# Spike S2-CLI — Agent Stop hook: does `decision:block` start another turn?

**Verdict: PASS, with a measured limit** (2026-11-24 23:41 WIB, kiro-cli 3.5.0 headless, engine v3 pinned). The IDE half
(S2-IDE) is a human step and is not covered here.

Harness: `spikes/kiro/setup-stop.sh <ws> <mode> <timeoutSeconds> [sleepMs]` adds a `Stop` hook running
`spikes/kiro/stop-hook.mjs`, which records its STDIN payload and, on its first call only, asks the agent to keep working
with the reason `SPIKE-S2-GATE: before you stop, call the search_rooms tool on the hollowinn server with guests=1 and reply with the line GATE-SEEN <number of rooms>.`
Prompt for every run (`prompts/turn-07.md`): `Reply with the single word READY and do nothing else.`
Command: `kiro-cli chat --no-interactive --agent-engine v3 --trust-workspace --trust-tools=@hollowinn "…"`.

| Mode | Hook file | Exit | Wall | Output (deciding lines) | Stop events recorded |
|---|---|---|---|---|---|
| `json`: STDOUT `{"decision":"block","reason":…}`, exit 0 | `"timeout": 30` | 0 | 15 s | `READY` · `[tool] @hollowinn/search_rooms` · `GATE-SEEN 3` | 1 |
| `exit1`: reason as plain STDOUT text, exit 1 | `"timeout": 30` | 0 | 14 s | `READY` · `[tool] @hollowinn/search_rooms` · `GATE-SEEN 3` | 1 |
| `slow`: sleeps 8 s, then like `json` | `"timeout": 5` | 0 | 11 s | `READY` only | 0 — re-run with an entry record: entry at 16:56:14.6Z, session ended 16:56:19.6Z, no completion record ever written |

Measured facts:
1. `decision:"block"` + exit 0 starts another agent turn, and the agent sees the supplied reason (it carried out the
   instruction that only the reason contained).
2. Exit 1 with the reason as plain text also starts another turn, and the agent saw that text too (same action, same
   answer). The docs only promise the reason for exit 0 + `decision:"block"`; on CLI 3.5.0 the exit-1 text reached the agent.
3. Timeout: a 5 s timeout on a hook that sleeps 8 s kills the hook, and the turn simply ends — the gate **fails open**. (The re-run's
   entry record proves the hook was invoked; it was stopped 5 s later, before its decision.)
4. Stop payload keys: `session_id`, `hook_event_name` (`"Stop"`), `cwd`. No transcript, no last message, no turn id.
5. **Limit:** in all three runs the continuation turn ended WITHOUT a second Stop event (one Stop record per run; the hook
   writes its record before deciding, so a second call would have been recorded). In headless CLI 3.5.0 the gate gets one
   block per user prompt; it cannot re-check what the agent did in the turn it started.

Consequences for the build (applied to the plan): the gate's real hook file sets `"timeout"` explicitly and its wall clock
must stay under half of it (E1–E3); the "3 blocks per session" cap is moot on the CLI — at most one block per prompt was
measured, so CLI evals E1–E3 assert one block + the agent's response to it, and any re-check runs as the next prompt's
Stop (or a `--resume-id` follow-up prompt); a public claim that the gate "loops until the jars are calm" is not made.
The IDE behaviour (S2-IDE) is unmeasured.

Credits (measured, `scripts/kiro-credits.mjs`): json 0.2557, exit1 0.2600, slow 0.0730, slow re-run 0.0730. Three earlier runs with mangled
hook arguments (a shell word-splitting slip, all three ran in `json` mode; same result: one block, `GATE-SEEN 3`, one Stop
record) cost 0.2604 + 0.2585 + 0.2603 and are kept only in the ledger.
