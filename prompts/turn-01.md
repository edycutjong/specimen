Create the three Kiro steering files for this repository. Each file starts with the front matter `---` / `inclusion: always` / `---` and nothing before it. Keep each file under 60 lines, plain and specific; write only these three files.

1. `.kiro/steering/product.md` — what SPECIMEN JAR is: a tool for people who build MCP servers. A Kiro hook captures every MCP tool call a Kiro agent makes (input and response) into an append-only "jar" (one JSON line per call, `jars/<session>.jsonl`). Later, `specimen replay --server "<cmd>"` replays every jarred call, in order and in a fresh server process per recorded session, against a changed version of the server, and diffs each response field by field. Each jar ends up PRESERVED (identical after normalisation), RATTLED (fields removed, changed or renamed), CRACKED (the tool is gone or now errors), SKIPPED (not allowed by `.specimen/replay.json`) or UNSEALED (not replayable). The verdict is SHIP only when at least one jar was compared and none is rattled, cracked, unsealed or skipped; otherwise HOLD with the reason. SHIP means "replay clean on the recorded set", never "this server is safe". A rattled jar is turned into a Kiro bugfix spec (Current / Expected / Unchanged behaviour) by a custom agent, so Kiro fixes the server through its own Bug Fix workflow. The demo server is `hollow-inn`, a small haunted-inn booking MCP server with versions v1, v2 (three deliberate breaks) and v2.1 (Kiro's fix). Deterministic code decides what broke; Kiro decides how to fix it.
2. `.kiro/steering/tech.md` — one TypeScript codebase (TypeScript 5 strict, Node 20+, ES modules, npm workspaces); `@modelcontextprotocol/sdk` 1.x (`McpServer`, `Client`, stdio transports in Node, `InMemoryTransport` in the browser); `zod` for every external format (jar lines, replay results, hook payloads); `commander` for the CLI; Vite + React 19 for the browser cabinet (static build, SVG jars, CSS animation, self-hosted fonts); `vitest` + `fast-check` for tests; `npm test` at the repo root runs everything. Rules: no mocks of the MCP protocol on any judged path; no network or font CDN calls at runtime; server modules have no `node:` imports so the cabinet can bundle them; every number shown to a user comes from a real run; never edit files under `jars/` (they are evidence).
3. `.kiro/steering/structure.md` — the layout: `packages/core` (jar schema, pairing, redaction, normalise, diff, verdict, check-spec — shared by everything), `packages/cli` (the `specimen` command: `hook`, `replay`, `file`, `check-spec`, `init`), `packages/mcp` (the specimen MCP server), `servers/hollow-inn/src/{v1,v2,v2_1}.ts` + `createServer(version)` run from source with `npx tsx servers/hollow-inn/src/main.ts <version>`, `apps/cabinet` (the browser cabinet), `jars/` (recorded evidence, read-only, `jars/MANIFEST.sha256`), `replays/` (replay results), `.specimen/` (`volatile.json`, `redact.json`, `replay.json`), `.kiro/` (hooks, steering, specs, agents, settings/mcp.json), `prompts/` (every Kiro prompt used to build this repo, numbered), `evidence/` (spike and run evidence), `docs/`, `spikes/` (day-1 spike harnesses, not product code). Tests live in `<package>/test/*.test.ts`.
