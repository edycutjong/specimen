1. `.kiro/steering/specimen-bugfix.md` — a steering file with the front matter `---` / `inclusion: auto` / `name: specimen-bugfix` / `description: How to write a Kiro bugfix spec around a SPECIMEN JAR repro block. Body (under 70 lines): the format of a bugfix spec filed from a jar, at `.kiro/specs/<slug>/bugfix.md`, in Kiro's bugfix format. Required sections in this order: `# Bugfix Requirements Document`, `## Introduction`, a repro block, `## Bug Analysis` with `### Current Behavior (Defect)` (numbered lines `1.n WHEN … THEN the system …`), `### Expected Behavior (Correct)` (`2.n WHEN … THEN the system SHALL …`) and `### Unchanged Behavior (Regression Prevention)` (`3.n WHEN … THEN the system SHALL CONTINUE TO …`). The repro block is written by the `specimen` CLI, not by the agent: it sits between the lines `<!-- specimen:repro:start -->` and `<!-- specimen:repro:end -->`, lists the accession id of every jar with the same change signature (ids look like `SPC-0004`), the recorded call, the recorded response, the replayed response and the field-level diff table; the agent must copy it byte for byte and never edit, reorder or summarise it. Expected Behavior must name the jarred reference it restores: the JSON pointer and its recorded value (for a rattled field), the removed ids (for a dropped list item) or the missing tool name (for a cracked jar). Unchanged Behavior cites the PRESERVED jars of the same tool by accession id. Never invent a value that is not in the repro block; never claim the server is safe; one spec per change signature.
