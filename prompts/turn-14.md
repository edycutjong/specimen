Start a new Feature spec, Requirements-First, named jar-capture. Write only .kiro/specs/jar-capture/requirements.md (EARS acceptance criteria, numbered requirements). Do not write design.md or tasks.md yet and do not change any other file.

The feature: when a Kiro agent calls a tool on a configured MCP server, Kiro's own PreToolUse and PostToolUse shell hooks capture the call into a "jar" — an append-only JSONL file of real recorded calls that is later replayed against a new server version. No proxy sits between Kiro and the server; the hooks are the only capture point.

What it must cover:
1. Jar line format "specimen v1", one JSON object per line in jars/<session_id>.jsonl, validated with a zod schema in packages/core: v (1), id (accession id SPC-0001, SPC-0002 … from a counter in .specimen/counter, assigned at write, never reused), session_id, seq (order of the call within the session), server (the configured server key), tool (tool name without the mcp_<server>_ prefix), tool_id (the raw tool_name Kiro reported, e.g. mcp_hollowinn_quote), input (tool_input after redaction), response_text (the tool_response string exactly as Kiro handed it to the hook), response (JSON.parse(response_text) when it parses, else null), t0 and t1 (ISO-8601, stamped by the hook processes because the payload carries no timestamp), duration_ms (t1 - t0, includes hook overhead), redacted (JSON pointers of redacted values).
2. "specimen hook pre [--server <key>]": reads the PreToolUse JSON payload on STDIN ({session_id, hook_event_name, cwd, tool_name, tool_input}) and appends {session_id, seq, tool_id, input_sha256, t0} to .specimen/pending.jsonl. input_sha256 is taken over canonical JSON (parsed, keys sorted recursively, no whitespace), never over the raw STDIN text, so a key-order difference between the pre and post payloads cannot orphan a call.
3. "specimen hook post [--server <key>]": reads the PostToolUse payload (the same fields plus tool_response, a string), pairs it FIFO with the oldest pending entry that has the same session_id, tool_id and input_sha256, and appends the jar line. A post with no matching pending entry is still written, never dropped, and is marked so a replay can tell. A pending entry that is never paired stays in pending.jsonl as an orphan for later quarantine.
4. Server resolution: --server <key> (written into the hook file) wins; without it, server = the longest configured server key s such that tool_name starts with mcp_<s>_, where configured keys come from .kiro/settings/mcp.json.
5. Hook contract: every hook command exits 0 and prints nothing on STDOUT, whatever happens (capture must never break or talk to the agent's call); diagnostics go to .specimen/hook.log.
6. Redaction from .specimen/redact.json {"keys": [...], "patterns": [...], "text": "redact" | "hash"} applies to tool_input and to the response before anything is written. For a JSON response, the values under redacted keys and string values matching the patterns (bearer tokens, API-key shapes, e-mail addresses) are replaced by "[REDACTED]" by editing those value spans in the raw text, never by re-serialising the parsed object; a response with nothing to redact is stored byte-identical. Example that must survive: the demo server writes money as two-decimal number literals such as "total":425.00, and the jar must keep 425.00, not 425. A response that is not JSON gets the patterns pass on its text and the line is flagged text_redacted: true. With "text": "hash" the text is stored only as sha256 plus length.
7. Firewall: "specimen hook firewall" on PreToolUse with matcher write exits 2 with STDERR "jars are evidence and read-only" when the write targets a path under jars/, else exits 0. Shell writes are outside the write category, so jars/MANIFEST.sha256 (sha256sum format, checkable with sha256sum -c) is written and verified by "specimen manifest write|check" and compared before and after every Kiro execution.
8. Kiro wiring: .kiro/settings/mcp.json registers the demo server under the key hollowinn (command: npx tsx servers/hollow-inn/src/main.ts v1); hook files .kiro/hooks/specimen-jar-pre.json and specimen-jar-post.json (matcher @hollowinn), specimen-jar-firewall.json (matcher write) and post-task-tests.json (PostTaskExec, runs npm test). Standalone hook file shape: {"version":"v1","hooks":[{"name","trigger","matcher","action":{"type":"command","command"}}]}.
9. Tests in vitest (and fast-check properties where they fit): canonical hash ignores key order, FIFO pairing, byte-identical storage, span redaction that keeps 425.00, the firewall decision, the hook's silent STDOUT and exit 0 on bad input.
